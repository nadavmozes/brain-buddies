# Shared progress-store refactor + NQ namespacing, mission rollover, pet moment, daily tile, local analytics

Batch 3 P1 folds the five sibling per-game stores (Shape Safari, Word Wizard, Clock Hero, Money Math, Memory Match) onto a shared `GameProgressStore` base, namespaces Number Quest's bare shared_preferences keys under `nq_` with a one-time migration, adds a midnight mission rollover guard, a small non-scary "Buddy grew" pet moment on result screens, a hub Daily tile that reuses NQ's daily level, and a local-only analytics sink. The whole point of the batch is behavior preservation: persisted keys, coin formulas, star thresholds, achievement sets, and unlock gating must stay byte-identical while the code is deduplicated. Verified by reading every sibling store against its `main` version, tracing the migration against NQ's old key set, and running the suite. Watch for: nothing blocking — all five stores are faithful, the NQ migration touches only NQ's own keys, the rollover persists the day before applying, and the pet moment renders nothing at 0 delta. **confirmed** via per-file diff and 15 green tests.

**Verdict**: APPROVED

## High-level view

The shared `GameProgressStore` carries the common per-level stars/fastest maps, the `<prefix>_sound`/`<prefix>_level_<id>`/`<prefix>_fastest_<id>` persistence loop, the unlock rule, and the `starsForPercent` (90/70/50) / `keepBestStars` / `recordFastestIfBest` helpers. Each of the five subclasses supplies only `keyPrefix` + `orderedLevelIds`, overrides `load`/`reset` to add its extras (best/rounds, plus Safari's befriended set), and composes the helpers inside its own `completeLevel`. Line-for-line the coin formulas, boss conditions, achievement id sets, and Outcome classes match `main`.

Number Quest stays off the base (it has XP/skills/streak concerns the siblings lack) but gets its bare keys moved under `nq_`. The one-time migration copies each known old NQ key to its `nq_` twin only when the twin is absent, then removes the old key, and never reads or writes a sibling's `safari_*`/`wizard_*`/etc. namespace. `reset()` removes the full `nq_*` set.

Mission rollover is a single `_rolloverMissionsIfNeeded` that mirrors `load()`'s stale-day branch and runs at the top of both `reportMission` and `claimMission`, persisting `_missionDay` and clearing progress+claimed before any new report or claim lands past midnight. `Missions.forDay`, `pet.dart`, and NQ's `level.dart` are untouched, so rotation, pet curve, and the daily-level definition are unchanged.

The pet moment is a transient (non-persisted) summary reset to 0 at the start of every `onRoundFinished`; the widget returns `SizedBox.shrink()` when no XP was fed, and the pet feed itself (`addPetXp(coinsEarned)`) is identical to before. The Daily tile reuses NQ's existing `GameScreen(isDaily: true)` with `WorldMap.dailyLevel()`, so the off-map id keeps it out of star/unlock progression while `onRoundFinished` still ticks streak/pet/missions. Analytics is local shared_preferences counters only, no network.

### Sibling stores fold onto GameProgressStore with identical persistence

Each sibling's `main` version was compared field-by-field against its refactored form. The base `load()` reads `<prefix>_sound` (default true), sets `SoundBridge.enabled`, then loops `orderedLevelIds` reading `<prefix>_level_<id>` and `<prefix>_fastest_<id>` — the same keys the standalone stores used. Subclasses call `super.load()` then read their extras: Safari `safari_best`/`safari_rounds`/`safari_befriended`, Clock/Wizard/Money `<prefix>_best`/`<prefix>_rounds`, Memory `memory_rounds` (no best). No key was renamed or dropped; `safari_befriended` and the four `_best` keys (all but Memory) persist. **confirmed**

Coin formulas are byte-identical: Safari `correct*3 + stars*5 + (guardian?20:0)`, Clock/Wizard/Money `correct*3 + stars*5 + (boss?20:0)`, Memory `pairs*3 + stars*5 + (boss?20:0)`. Boss/guardian conditions match `main` (`level.isBoss && percent >= 70` for Clock/Wizard/Money; Memory `level.isBoss`; Safari passes `guardianBefriended` through). Achievement id sets per game are unchanged (`firstGame`+`perfectRound`+per-game master +`threeStar`+`speedster`, Safari adding `guardianFriend`/`shapeExplorer`). Each `*Outcome` class and its fields are unchanged. **confirmed**

`starsForPercent` reproduces the 90/70/50 ladder exactly. `keepBestStars` only writes when `newStars > stars(id)` (keep-best preserved). `recordFastestIfBest` writes only when `earnedStars == 3 && elapsedSeconds > 0 && (prev == 0 || elapsed < prev)` — the fastest-only-on-3-star-and-improved rule. Memory's `wrongFlips` curve (`0→3`, `≤pairs→2`, else `1`) is carried verbatim and does not route through `starsForPercent`. **confirmed**

### Number Quest namespacing and one-time migration

NQ keeps its own `ChangeNotifier` (XP, skills, streak-free) and moves its bare keys to `nq_`: `nq_xp`, `nq_sound_on`, `nq_best_answer_streak`, `nq_mult_correct`, `nq_level_<id>`, `nq_fastest_<id>`, `nq_<skill.key>_correct/attempts`. `_migrateLegacyKeys` builds an old→new map over exactly those keys (plus the bool `sound_on`), and for each copies only when the new key is absent and the old key present, then removes the old key. It never enumerates or touches another store's namespace, so existing XP/stars/fastest/skills/sound survive and sibling keys are safe. `reset()` removes the full `nq_*` set including per-skill keys. The old `daily_streak`/`last_day` keys are not NQ's concern here (streak moved to `PlayerProfile` in a prior batch); the migration correctly leaves them alone. **confirmed** — covered by the `migrates legacy keys to nq_ without touching others` test.

### Mission rollover persists the day before applying

`_rolloverMissionsIfNeeded` sets `_missionDay = today`, clears `_missionProgress` and `_missionClaimed`, persists `_kMissionDay`, and removes the two persisted mission maps — the same effect as `load()`'s stale-day else-branch. It runs at the very top of `reportMission` (before the `amount <= 0` early return, so a zero report still rolls the day) and `claimMission` (before the claimable check). A session left open past midnight therefore resets yesterday's progress and claimed set before a new report or claim is counted. `Missions.forDay` is unchanged (no diff to `mission.dart`), so the deterministic 3-mission rotation is intact. **confirmed** — covered by the rollover test.

### Pet moment is transient, friendly, and zero-safe

`onRoundFinished` resets the four `_lastRoundPet*` fields to 0/false at entry, captures `beforeLevel`/`beforeStage`, feeds `addPetXp(coinsEarned)` (unchanged), then records `_lastRoundPetXp = coinsEarned`, the new level, and level/stage-change flags. None of these are persisted, so they are a per-round display summary only. `PetRoundMoment` returns `SizedBox.shrink()` when `lastRoundPetXp <= 0`, and otherwise shows the pet emoji, a `+N XP` row, and a cheerful "🎉 Buddy grew!" banner on level/stage change — small and non-scary for ages 6-9. The pet XP fed is the same `coinsEarned` value as before the batch. **confirmed**

### Daily tile reuses NQ's daily level without touching progression

The hub `_openDailyChallenge` lazily loads the shared NQ `GameState`, calls `recordGamePlayed`, and pushes NQ's existing `GameScreen(level: WorldMap.dailyLevel(), isDaily: true)`. NQ's `completeLevel` guards fastest/stars with `onMap = WorldMap.allLevels.any(...)`, so the off-map daily id (999) records no stars or fastest and cannot unlock a map level, while `profile.onRoundFinished(...)` still runs to feed streak/pet/missions/analytics. The `isDaily` plumbing pre-existed on `main` (the diff to `game_screen.dart` is only the new `AnswerBadge` overlay). **confirmed**

### Local-only analytics sink

`PlayerProfile` gains an optional `AnalyticsSink` attached once at the hub after `AnalyticsService.load()`, and `onRoundFinished`/`recordGamePlayed` push aggregate counts and snapshots. `AnalyticsService` persists only via shared_preferences `getInt`/`setInt` — no `http`, `HttpClient`, socket, or `Uri` usage — matching the "option A, local storage, kid-friendly" directive, so no data leaves the device and there is no new trust boundary. **confirmed**
